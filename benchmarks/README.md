## 本次结果

2026-10-13，在 Ryzen 9 7900X、Ren’Py 8.5.3 内置 Python 3.12.8、pysqlite3／SQLite 3.51.1 上完成。三档、三模式、三次重复共 27 次模式测试，以及 3 次公开导入全部成功；每个条件有 36 个 warm has 和 36 个 warm query 样本。各阶段结果通过独立公式核对；完整集合核对由小规模测试覆盖。

百万角色包含 **1,524,372 条事实**，预期 CanEnter 为 **4,100,000 行**。下表时间为中位数；峰值 RSS 为三次进程的最大值。

| 模式 | warm has | warm query | 单条提交 | 完整快照 | 修改后恢复 | 峰值 RSS |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| cached | 6.165 ms | 85.410 ms | 4.408 s | 4.334 s | 8.433 s | 1328.1 MiB |
| live | 699.741 ms | 277.919 ms | 4.425 s | 4.322 s | 8.373 s | 1211.5 MiB |
| materialized | 6.163 ms | 85.531 ms | 6.293 s | 4.351 s | 10.186 s | 1327.8 MiB |

cached 恢复后首次 has 为 **1.836 s**；单条修改后的首次 has 为 **1.862 s**。其单条提交与修改后首次读取分别测量，不能把 4.408 s 当作这一行动的全部成本。100 条事实在一个 batch 内提交为 **4.339 s**，说明本次写入主要受共享的全量保存成本影响；具体阶段占比仍需独立剖析。

百万档公开逐条 add 导入一次为 **123.774 s**，包含一个 batch 的提交和快照；不能据此估计原生批量 SQL 导入速度。压缩快照 **4.956 MiB**，与运行峰值内存差别很大。

这份基线支持下一轮先做两个独立对照：**完整快照表示／生成方式**、**派生表字段索引**。前者需要继续满足 Ren’Py 每次行动的保存和回滚约定；后者同时衡量读取收益、物化时间与内存。保留本次原始后端作为对照，不把多个优化混在一个结果中。更精细的依赖失效可以随后单独验证。

## 复现

在项目根目录安装锁定依赖，然后运行：

```sh
uv sync --locked
uv run --locked python benchmarks/run.py
```

默认是 10,000／100,000／1,000,000 角色，三个模式各三次重复，串行执行；每次重复各有 12 次 warm has、12 次 warm query。每档公开导入仅测一次。生成规模、重复次数、查询次数、batch 大小、子进程超时均可通过命令行修改。

本次正式结果使用 Ren’Py 8.5.3 Linux SDK 的 Python 及示例已安装的运行依赖：

```sh
uv run --locked python benchmarks/run.py \
  --python /path/to/renpy-sdk/lib/py3-linux-x86_64/python \
  --packages examples/palace/game/python-packages \
  --out benchmarks/results/my-sdk-baseline
```

SDK 对应的依赖安装方式见项目 README。输出目录必须为空，默认使用带时间的独立目录；`.work` 中的生成快照、日志和阶段检查点不提交。失败／超时返回非零状态，已经完成的阶段保留，但不加入成功样本统计。重跑使用新目录。

## 如何解释结果

- `cached` 首次资格判断包括三个依赖关系的完整物化；事实变更后会再次付出这一成本。`materialized` 将同一成本提前到恢复和提交阶段；不能只用首次读取速度比较两者。
- 首次读取固定为编号靠前的角色 3；`has` 找到一行即停止，所以 materialized 的 first 可能明显快于分散正负样本的 warm。它们的查询参数不同，不能解读为 warm 反而拖慢了系统。
- 提交与快照成本随整个事实集增长。当前每次实际提交都查询全部事实、构建 Python 字典和 JSON，再压缩；因此单条修改也会产生完整世界的保存成本。batch 能把多次保存合并为一次，不能消除这一次成本。
- 已缓存关系也不是常量时间查询。当前派生 TEMP TABLE 没有字段索引；按角色过滤仍可能扫描。报告中的 warm query 增长与这一结构一致。索引的独立收益需要后续对照实验确认。
- 压缩快照大小不能代表运行内存。数据规则性强、容易压缩，运行中还存在 Python 对象、SQLite 表和原子恢复／重载的候选世界。

本轮仅覆盖 palace 的固定规则及均匀分布，证明的是“大事实集上的当前实现成本”。它没有覆盖大规则集、递归深度、严重倾斜的数据、高频撤销，以及完整 Ren’Py 界面、历史追踪和存档归档。派生行数是公式期望值；小数据完整集合核对，大数据按独立公式检查正负样本。

临时存储方式取决于 SQLite 驱动。此次 pysqlite3 的编译选项包含 `TEMP_STORE=3`，因此临时表／临时索引使用内存，即使 `PRAGMA temp_store` 的默认返回值为 0。其他驱动可能使用磁盘，不能直接套用此次内存结果；原始 JSON 同时记录这两个设置。参见 [SQLite 临时文件说明](https://www.sqlite.org/tempfiles.html)。
