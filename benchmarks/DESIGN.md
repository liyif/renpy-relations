# 大规模关系基准设计

目标：测量当前后端在大事实集上的读、写、保存、恢复和规则重载成本，给三种执行模式提供可比较的证据。本轮保持后端实现不变，不先做性能优化。

## 数据与规则

使用现有 palace 的真实 Logica 编译链路和三个导出关系：CanEnter、CanInvestigate、CanClaimReward。编译耗时属于构建阶段，单独记录，不混入运行时。

固定、无随机的数据分布：

- N 个角色，每人加入一个阵营，32 个阵营循环分配。
- 每个阵营授予 archive、garden、hall、tower 四处访问资格，共 128 条固定事实。
- 角色编号为 10 的倍数时，另有 vault 的个人担保。
- 编号为 3 的倍数时，知道 forged_letter。
- 编号为 11 的倍数时，已领取 investigation 奖励。

事实数为 `128 + N + ceil(N/10) + ceil(N/3) + ceil(N/11)`。预期 CanEnter 行数为 `4N + ceil(N/10)`；CanInvestigate 为 `ceil(N/3)`；CanClaimReward 为 `ceil(N/3)-ceil(N/33)`。报告明确区分生成的事实数与根据公式计算的预期派生行数。

默认规模为 10,000／100,000／1,000,000 个角色。小规模测试通过公开 query 完整核对关系集合；大规模每阶段用独立 Python 公式核对分散的正／负样本，不把全量 Python 结果解码混入通常的按角色查询。

## 测量路径

每档先在独立进程通过公开 add 和一个 batch 生成世界，记录一次完整导入耗时（含提交和快照），保存逻辑快照。它不是绕过接口的批量 SQL 导入。

每个“规模 × 模式 × 重复”启动新进程，从同一份快照开始：

1. 创建空后端，再恢复初始世界；恢复包括 schema／规则准备和完整事实导入。
2. 首次读取角色 3 的奖励资格（cached 会物化全部依赖；materialized 在恢复时计算；live 在读取时执行）。这一角色位于数据前部，first 不代表任意角色的查询延迟；分散角色见 warm 样本。
3. 重复 has 与按角色 query，包含分散角色及不存在的角色。记录逐请求样本。
4. 显式生成完整事实快照，记录时间和字节数。
5. 单条知识事实变更提交，再记录更新后首次读取。
6. 一个 batch 写入最多 100 条新的知识事实，再记录更新后首次读取。变更选择编号靠前、原先无知识且未领奖的角色；更新后的读取确认对应角色资格改变。每次提交均包含后端现有的完整快照生成成本。
7. 重载相同规则文件，测量实际候选验证／预执行／切换路径，再记录首次读取。
8. 从原快照恢复已经修改的世界，并读取结果，验证恢复撤销变更。这一阶段同时存在旧世界和候选世界，与最初空世界的加载分开记录。

每阶段记录墙钟时间、进程 CPU 时间、阶段前后 RSS、截至该阶段的进程峰值 RSS。峰值是整个独立进程的累积高水位，不冒充某一阶段的独立内存增量。Python、SQLite、SQLAlchemy、CPU、平台、源码摘要和 Git 版本随结果保存。

默认每个条件三次独立重复，顺序轮换，串行运行，避免同一台机器上并行压力互相污染。查询参数固定且跨重复相同。warm 表示同一个实例已执行过关系读取，不表示清空操作系统文件缓存后的冷启动。逐请求 p95 仅描述本次小样本，不视为生产尾延迟保证。

## 运行环境与结果

使用 uv 启动父进程。默认子进程使用 uv 环境；可指定 Ren’Py SDK 的 Python 和匹配的 python-packages，用相同后端代码测量内置运行时。大规模实测优先采用后者，明确不包含 Ren’Py 界面、交互调度、历史追踪和存档归档成本。

输出原始 JSON、长格式 CSV 和 Markdown 汇总。原始阶段结果及时落盘；超时／异常保留已完成阶段，标出失败状态和样本数，不把缺失结果填零或计入成功中位数。完整运行失败返回非零退出码。

生成的大型快照和运行中间文件不提交。提交可重复的数据生成器、基准脚本、测试、设计、实测结果及解释。SQLite TEMP 对象可能使用磁盘，不能仅由内存主库推断所有临时数据均在 RAM；记录驱动默认 temp_store 和编译选项供解释。

参考：[SQLite 临时文件](https://www.sqlite.org/tempfiles.html)。
