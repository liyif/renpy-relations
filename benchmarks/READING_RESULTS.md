# 如何阅读 Benchmark 结果

这些实验测量 Ren’Py Relations 的公开接口及其数据库实现。数值包含 Python、SQLAlchemy、数据库执行和结果转换等实际调用成本，不是数据库引擎单独执行 SQL 的成绩，也不是完整游戏的帧耗时。

[当前报告](results/current/REPORT.md)汇总关键数值，各子报告展示更多配置，JSON 保留阶段、环境、校验与源码身份。运行方法和覆盖范围见 [Benchmark](README.md)。

## 先分清五种规模

| 名称 | 指什么 |
| --- | --- |
| 事实 | 已写入数据库的事实行数，不是事实表的数量 |
| 条件 | 一轮中实际调用一次 `has()` 的不同派生关系数 |
| 总派生关系 | 条件加共享前置关系；条件测试额外包含 64 个前置关系 |
| 角色 | 大事实集生成器中的角色数；每个角色可能对应多条事实 |
| 依赖链长度 | 派生关系的依赖深度，不是事实数或一次查询返回的行数 |

例如“1000 条件／107 事实”表示：数据库有 107 行事实、1064 个派生关系，一轮逐个读取其中 1000 个条件。它不是对同一条件调用 1000 次，也不是一条 SQL 一次返回 1000 个判断。1:1／约 1:10 是事实行数与总派生关系数的配比。

## 查询模式把计算放在哪里

三种模式回答相同的问题，但计算发生的时机不同。

| 模式 | 加载与写入时 | 读取时 |
| --- | --- | --- |
| `cached` | 加载声明和依赖图；修改事实后标记受影响关系失效 | 按需创建和重建完整派生关系，再过滤查询；有效关系复用 |
| `materialized` | 加载时计算空世界的全部派生关系；提交时重建受影响关系 | 从已经计算好的派生表读取 |
| `live` | 加载时建立视图；提交只修改事实 | 通过视图执行推导查询 |

因此，“首轮读取很快”可能意味着计算已在导入或提交时完成。比较模式时，应结合加载、导入、提交和随后读取，不能只选最快的一列。

`cached` 保存的是数据库内的完整派生关系，不是某组查询参数对应的 Python 返回值。warm 读取仍要执行查询、过滤并返回结果。

## 一、大量派生条件：一次检查许多剧情前提

对应 `conditions-sqlite`、`conditions-duckdb`，由 `conditions.py` 调用 `rules.py` 的 worker。这里使用生成器同步构造 SQL 和已知依赖，控制条件数、共享关系、否定条件与真假分布；不测大规则集的 Logica 编译。

每次计时试验按以下顺序执行：

```text
加载空世界 → 导入事实 → 首轮读取 → 再读一轮
→ 局部修改并读取 → 全局修改并读取 → 无关修改并读取
```

| 报告列／原始阶段 | 实际测量内容 |
| --- | --- |
| 加载／`load` | 已读入 JSON 字典的规则包校验、SQLAlchemy 表定义、数据库及后端初始化、原生依赖排序，以及该模式需要的派生对象。包括 `RuleSet` 与 `LogicDB` 构造，不含 JSON 文件读取、进程启动或 Logica 编译 |
| 导入／`ingest`，见 JSON | 在一个 batch 中通过公开 `add()` 写入生成事实并提交；materialized 模式还会重建受影响推导。该阶段在首轮读取之前完成 |
| 首轮／`cold_panel` | 对每个不同条件调用一次 `has(name, flag="v0")`。cached 首次物化所需依赖，materialized 已在导入时计算，live 执行视图查询 |
| 重复轮、warm 轮／`warm_panel` | 世界状态不变，再逐个读取同样的条件；cached 复用有效派生关系，live 仍执行推导 |
| 局部动作／`local_commit` + `local_panel` | 将第 0 个领域的一个状态关闭并提交，然后读取全部条件 |
| 全局动作／`global_commit` + `global_panel` | 关闭全部最终条件共享的全局开关并提交，然后读取全部条件 |
| 无关动作／`unrelated_commit` + `unrelated_panel` | 修改不被条件读取的备注事实并提交，然后读取全部条件 |
| 局部重建数／`local_rebuilt` | 局部修改后的读取实际重新物化了多少个关系，包含需要重建的前置关系；不是修改的事实数。报告只在 cached 模式展示 |
| warm 单次中位数／p95 | 一轮中的各次 `has()` 延迟分布，子报告使用微秒；其余整轮时间通常使用毫秒 |

**动作列是“提交＋整轮读取”，不是一次写入的延迟。** 条件主矩阵没有绑定历史镜像接收者，提交不生成快照；它也不包含对白、菜单、渲染、Ren’Py 存档归档或长期回退历史。

### 修改是依次累计的

| 阶段 | 读取时的世界状态 |
| --- | --- |
| 首轮、warm 轮 | 初始事实，全局开关打开 |
| 局部动作后 | 第 0 个领域的一条状态已关闭 |
| 全局动作后 | 保留局部修改，并关闭全局开关；最终条件均为假 |
| 无关动作后 | 保留前两次修改，只额外修改备注；最终条件仍均为假 |

因此，各动作不是从同一个初始镜像独立开始的。尤其是“无关动作”在全局关闭后的状态上测量，不能直接把它与初始 warm 轮的差值当作无关写入的净开销。JSON 中的提交与读取阶段可分开查看。

### 两种事实布局在比较什么

`partitioned` 把 32 个领域的状态放在不同事实表；`shared_table` 把它们放在同一张表，用领域字段区分。失效按表级依赖传播，不识别修改了哪一行，所以共享表中的局部修改可能使所有领域的条件失效。

例如，当前 10000 条件、1:1、cached 的局部修改，分表布局重建 315 个关系，共享表布局重建 10064 个。这说明失效范围不同；动作总时间仍包含读取全部 10000 个条件，不能按重建数量直接换算速度倍数。

### 正确性校验在测量之外做什么

计时进程逐次核对 `has()` 的真假，整轮时间也包含循环、计时采样与这些断言。另有独立校验进程，对初始、局部修改、全局关闭、无关修改，以及重新打开全局开关并添加阻断事实这五种状态核对完整行集合。第五种状态只用于校验，不是额外的动作计时列。

独立校验避免在计时之前把所有派生关系预热。试验的阶段 JSON 写入位于计时边界之外；它们仍会计入整个子任务的墙钟时间。

## 二、大事实集：事实和派生结果变大以后

对应 `facts-sqlite`、`facts-duckdb`，由 `run.py` 执行。使用 palace 的三条导出规则，增加角色、成员资格、通行许可、知识和已领取奖励等事实。这是“少数规则处理大量数据”的压力测试，不是前面的千至万个条件测试。

角色数不等于事实数。例如百万角色会产生 1524372 行事实，预期 `CanEnter` 产生 410 万行。派生行数是固定生成公式给出的数量；小规模测试核对完整集合，大规模测量使用分散的正负样本验证。

每档先运行一次 `seed` 生成共享事实镜像，再为每个查询模式启动三个独立 `measure` 进程。

JSON 中的 `compiler.seconds` 是父进程为 palace 生成所选后端规则包的总耗时，包含 Logica 编译和构建验证。它不属于下面的 worker 阶段，也不代表千至万个生成条件的编译时间。

| 原始阶段 | 实际测量内容 |
| --- | --- |
| `init_empty` | 从规则文件创建空世界，包括文件读取和 JSON 解析；这里与条件测试的 `load` 边界略有不同 |
| `public_ingest`，仅 seed | 在一个 batch 中逐条调用 `add()`，包含 Python 数据生成、参数绑定和提交；不是原生批量导入吞吐 |
| `snapshot`，seed | 首次生成完整事实镜像。把镜像写到供后续进程读取的 fixture 文件不计入这个阶段 |
| `restore_initial` | 从已读入内存的事实镜像构建并切换候选世界，建立该模式需要的派生对象；不含 fixture 文件读取 |
| `first_has` | 恢复后第一次判断指定角色是否能领取奖励；cached 可能在此构建完整所需派生关系 |
| `warm_has` | 对分散的角色逐次做奖励资格判断，包含正例、反例及不存在的角色 |
| `warm_query` | 逐次查询某个角色可进入哪些地点，返回少量字典行；不是一次返回整个派生表 |
| `snapshot`，measure | 恢复后、事实未修改时获取镜像；复用恢复时保存的输入字节串，测的是复用开销，不是完整导出 |
| `single_commit` | 添加一条新的知识事实并提交；不含历史镜像发布。materialized 包含受影响关系重建 |
| `first_has_after_single` | 单条修改后首次检查新资格，单独记录延迟到读取时发生的计算 |
| `batch_commit` | 在一个事务中添加多条知识事实；实际条数见 `batch_changes`，当前配置上限 100 条 |
| `first_has_after_batch` | batch 后首次检查其中一个角色的新资格 |
| `reload_same_rules` | 用当前事实重新加载同一份规则，包含必要的事实镜像生成、候选世界构建和新推导预执行；不是重新编译 Logica |
| `first_has_after_reload` | 重载后首次检查资格；cached 模式的候选预执行不会保留为有效缓存 |
| `restore_after_edits` | 恢复最初镜像，撤销后来的知识修改，包含候选世界构建与交换 |
| `first_has_after_restore` | 恢复后读取并确认新资格已经撤销 |

根报告的大事实表只选取 cached 模式的一部分指标；其余模式与阶段见子报告、`phases.csv` 和 JSON。

warm 只表示已经读过，并不表示过滤是常数时间。当前派生表没有业务字段索引，按角色过滤已物化关系也可能扫描大量派生行。

## 三、快照与历史提交：保存世界状态的成本

对应 `snapshots`，由 `snapshots.py` 执行。用单张事实表构造 1 万、10 万、100 万行数据，只配一条简单派生关系，不测试大量条件重建。初始化采用原生 SQL，排除在计时之外。之后通过公开接口修改事实，分别测量普通世界和绑定镜像接收者的世界。

| 报告列／原始字段 | 实际测量内容 |
| --- | --- |
| 普通提交／`plain_commit` | 在未绑定接收者的世界中添加一条事实并提交，不生成历史镜像 |
| 历史提交／`history_commit` | 在另一实例中添加一条事实、提交、生成完整镜像并调用接收回调；此前恢复基准镜像的准备工作不在此计时内 |
| 首次镜像／`snapshot` | 先修改事实使旧镜像失效，再计时生成完整镜像；前面的事实修改不在这一列内 |
| 复用镜像／`snapshot_reused` | 世界不变，立即再次调用 `snapshot()`，直接复用已有字节串 |
| 恢复／`restore` | 从内存中的镜像恢复到候选世界，再交换实例；不含首次派生读取或游戏存档解压 |
| 镜像 MiB／`snapshot_bytes` | 完整镜像字节数，包含事实、索引、数据库元数据及格式开销；不保存 TEMP 派生表和依赖图 |

“首次镜像”指缓存失效后的完整生成，不是每个数据库终生只会发生一次。普通提交和历史提交使用不同实例，不能把两列相减当作独立测得的精确序列化耗时。

当前 SDK 测量中的 pysqlite3 使用原生 backup，经临时文件取得镜像；DuckDB 使用原生数据库复制和文件镜像。标准 Python 的 sqlite3 可走 serialize／deserialize，但当前报告未测该驱动。这些列包含项目选用的实际保存路径，不是只比较两个同构的序列化函数。

历史回调只接收镜像，不保留长期历史。这里不测 Ren’Py 对多个历史节点的保留、压缩、存档文件写入或界面响应。

## 四、依赖长链：深度增加以后能否正确执行

对应 `graph`，由 `graph.py` 执行。构造 `Seed → Rule0 → Rule1 → …`，只插入一条事实。

| 字段 | 实际测量内容 |
| --- | --- |
| 加载／`load_seconds` | 从已生成的字典构造规则集与 cached 世界，包含原生图排序；不含生成字典或 Logica 编译 |
| 首次读取／`first_read_seconds` | 插入 Seed 后查询链尾，按需物化整条依赖链；不包含此前写入 Seed 的时间 |
| 状态 | 还会撤销 Seed 并确认链尾变假；这一步是正确性检查，没有单独的计时列 |

128／512／1050 是链长，每个后端每档只测一次。它测试深依赖的加载、物化和失效，不代表同样数量的浅层独立条件，也不是多次重复的中位数。

## 五、大条件加载探针：能加载不等于整轮查询快

对应 `duckdb-load-3000`、`duckdb-load-10000`，由 `suite.py --probe` 执行。使用与条件测试相同类型的生成规则、分表布局、约 1:10 配比和 cached 模式。

| 原始阶段 | 实际测量内容 |
| --- | --- |
| `load` | 构造规则集与空世界、建立声明与依赖图并执行原生排序，不含生成器准备或 Logica 编译 |
| `ingest` | 通过公开接口导入少量事实 |
| `first_has` | 只读取一个指定条件及其依赖，不读取全部 3000／10000 个条件 |

因此，10000 条件探针通过说明该配置能在预算内加载、导入并正确执行一次指定读取，不能据此得到 10000 条件的整轮延迟或完整正确性结论。每档只有一次观察，不能与主矩阵的三次重复中位数视为同一统计口径。

## 统计、状态与来源怎么读

当前受控报告的 8 个任务共保存 222 个子记录，组成如下。记录数包含重复、准备和正确性校验，不是 222 种不同性能配置。

| 负载 | 子记录组成 |
| --- | --- |
| SQLite 条件矩阵 | 108 次计时＋36 次独立集合校验 |
| DuckDB 代表条件配置 | 9 次计时＋3 次独立集合校验 |
| SQLite 大事实集 | 3 次 seed＋27 次模式测量 |
| DuckDB 大事实集 | 1 次 seed＋9 次模式测量 |
| 快照 | 3 档规模 × 2 种驱动 × 3 次独立重复，共 18 次 |
| 长链 | 3 档深度 × 2 个后端，共 6 次 |
| 大条件加载探针 | 2 档规模，各 1 次 |

| 项目 | 含义 |
| --- | --- |
| 子任务墙钟秒 | 启动到完成整个任务的时间，包含准备、多个 worker、独立校验、结果写入等；不是某次数据库操作延迟 |
| 整轮中位数 | 条件负载先测完整一轮，再对三个独立进程取中位数；不是单次条件延迟 |
| 动作中位数 | 先在每个进程内相加提交与随后整轮读取，再跨进程取中位数；不是两列中位数相加 |
| 条件单次中位数／p95 | 每个试验先计算请求分布，再对各试验的中位数／p95 分别取中位数；不是把全部请求合并后的分位数 |
| 大事实 warm 中位数／p95 | 合并相同配置的完整成功进程所保留的逐请求样本，再计算分位数 |
| 快照中位数 | 每进程先汇总自己的顺序样本，再跨独立进程汇总；当前配置每进程一次样本、三个独立进程 |
| CPU 秒 | 对应阶段的进程 CPU 消耗，与等待和文件 IO 在内的墙钟时间不同 |
| RSS／峰值 RSS | 进程驻留内存及整个进程生命周期的高水位；包括运行库、查询结果、校验和候选世界，不能当作单次查询新增内存 |
| `ok`／`completed` | 前者是子记录成功，后者是任务全部预期计时和校验记录完成；两者不是延迟数值 |
| `budget_limited` | 达到时间预算，保留已有阶段记录；不是通过，也不是精确完成耗时 |
| `failed`／`incomplete`／`missing` | 失败、记录不完整或结果缺失；不补零，不作为完整成功配置参与根报告汇总 |
| `running`／`current_phase` | worker 在阶段开始前写下的检查点；若进程被停止，原始文件可能保留此状态，是否完成要结合 `execution.json` 和套件状态判断 |

“独立进程”隔离 Python 和数据库状态，不会清空操作系统页缓存；“首轮”也不是物理冷磁盘读取。保持自动 GC 会保留正常程序中的分配与回收成本。后端当前均为同步单线程，DuckDB 配置 `threads=1`，结果没有体现其多核分析上限。

当前报告只测 `native` 变体。原始配置中出现 `baseline_ref` 不表示实际执行了历史对照；应查看 `variants`、每条记录的 `variant` 或 `legacy` 字段。

`measured_source` 记录测量源码哈希，`report_generation_source` 描述报告生成时的源码。工作树中的实际文件以 SHA-256 识别，基础 Git 提交不等于所有已测修改都已经位于该提交。`SHA256SUMS` 检查报告与原始文件的完整性，不替代结果正确性校验，也不证明在其他机器上有相同速度。

阅读顺序可以是：先看任务是否完成和环境身份，再选同一规模、布局、模式下的阶段比较，最后查看原始分阶段数据解释差异。完整游戏性能还需结合实际每次交互读取多少条件、修改哪些事实，以及是否发布历史镜像。
